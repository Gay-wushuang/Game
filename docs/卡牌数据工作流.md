# 卡牌数据工作流

## 数据源边界

- MySQL `law_evolution` 是开发期锦囊牌主数据源，只供策划导入、校验和导出使用。
- Godot 客户端不直连数据库；运行时只读取 `data/generated/cards.generated.json`。
- `docs/卡牌类型/主动锦囊v2.xlsx` 与 `docs/卡牌类型/被动锦囊v2.xlsx` 是当前唯一设计审核表；每行一张卡。
- `data/generated/cards.generated.json` 是由 V2 审核表生成、可版本控制的运行时权威快照；旧 `机制文本/锦囊卡/锦囊卡.md` 不再存在，也不得作为实现依据。

## 字段规范

- `card_kind` 只能为 `ACTIVE` 或 `PASSIVE`。
- V2 表中的功能描述已规范化为关键词、规则文本、触发键和参数。
- `card_id` 是程序稳定 ID；`design_code` 是策划编号，主动为 `TA-*`，被动为 `TP-*`。
- 规则分发使用 `handler_key` 和 `trigger_key`，禁止依赖中文卡名判断逻辑。
- 正式卡牌的 `logic_mode` 统一为 `LUA`，且每张卡必须填写唯一的仓库内 `lua_script`。

## 运行时规则层

- `BattleState` 和 `BattleEventBus` 保存并派发可测试的战斗状态与事件。
- `CardResolver` 将正式卡牌统一交给 `LuaCardRuntime`；不存在正式卡牌的内置规则回退路径。
- Lua 状态默认不开启 Lua 标准库和 Godot API，只注入 `heal_target`、`damage_target`、`draw_cards`、费用修改等白名单函数。
- Lua 不直接持有 `UnitState`、`DeckState`、场景节点或系统对象；所有状态变化都通过 `CardApi`。
- 当前30张锦囊均拥有独立 Lua 入口。每个入口必须显式调用与本牌 `handler_key` 同名的 `resolve_card_effect("...")`；具体数值只从运行时卡牌定义读取，不允许在 Lua 中复制 fallback 数值。
- `CardApi.SupportsHandler` 必须覆盖运行时快照中的全部 handler；遇到未注册 handler 时直接报错，禁止静默空结算。
- 敌我阶段触发必须使用方向明确的事件键，例如 `ALLY_BATTLE_PHASE_STARTED` 与 `ENEMY_BATTLE_PHASE_STARTED`，禁止用含义不明的通用阶段键。

## 本地重建

1. 编辑并审核两份 V2 Excel，确保 `validation=PASS`。
2. 由 V2 表生成 `data/generated/cards.generated.json`。
3. 执行 `dotnet build .\法则演进.csproj -warnaserror`。
4. 运行 `tests/training_arena_smoke.tscn`。

`CardDefectRegressionTest` 会在训练场 Smoke 中实际执行 V2 handler、Lua 对应关系、AP 最低值、治疗、伤害、护盾、怨恨、跨牌堆检索、临时复制、复活和攻击重定向回归；不得恢复为 COMPILE-ONLY 占位断言。

数据库密码只通过 `LAW_DB_PASSWORD` 环境变量传入，不写入仓库。仓库内隔离的本机开发实例放在 `.local/`，该目录已被 Git 忽略。

训练场设置中的“重新加载并校验全部卡牌脚本”会重建沙盒 Lua 状态并逐张编译脚本；不需要重新编译 C#。
